Резервное копирование, а не синхронизация. Отправляйте хранилище Obsidian на **свой собственный**
Google Drive, забирайте его обратно на новом устройстве и при желании шифруйте выбранные папки ещё
до того, как они покинут ваше устройство.

Работает и на компьютере, и на телефоне — без Node API, без `fetch`, без зависимостей в рантайме.

## Что он делает и чего намеренно не делает

| Делает                                                | Не делает                                       |
| ----------------------------------------------------- | ----------------------------------------------- |
| Загружает файлы, изменённые с прошлой отправки        | Трёхстороннее слияние                           |
| Восстанавливает хранилище целиком на новом устройстве | Синхронизацию в реальном времени или фоновую    |
| Шифрует выбранные пути на стороне клиента             | Никогда не удаляет ничего локально              |
| Отказывается перезаписывать правки другого устройства | Не переносит удаления (пока вы не включите это) |
| Сообщает о конфликтах и идёт дальше                   | Не хранит историю или версии файлов             |

Если вам нужен движок синхронизации — это не тот инструмент. Geode запускают перед рискованным
изменением хранилища и на новом ноутбуке.

## Установка

### Из релиза

1. Скачайте `main.js` и `manifest.json` из
   [последнего релиза](https://github.com/lif0/geode-drive-backup/releases).
2. Положите их в `<ваше хранилище>/.obsidian/plugins/geode-drive-backup/`.
3. Перезапустите Obsidian и включите **Geode** в _Settings → Community plugins_.

### Из исходников

```bash
git clone https://github.com/lif0/geode-drive-backup.git
cd geode-drive-backup
npm install
npm run build          # typecheck + lint + тесты + сборка
```

Скопируйте `main.js` и `manifest.json` в папку плагина внутри хранилища либо сделайте туда симлинк
репозитория и запустите `npm run dev` для сборки в режиме наблюдения.

## Настройка: ваш собственный OAuth-клиент Google

Geode никогда не прогоняет ваши заметки через третью сторону, поэтому учётные данные Google вы
предоставляете сами. Это разовая работа минут на десять.

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) и создайте проект.
2. **APIs & Services → Library** → включите **Google Drive API**.
3. **APIs & Services → OAuth consent screen**. В нынешней консоли это открывает **Google Auth
   Platform**. Нажмите **Get started** и заполните название приложения, свой адрес как support
   email, **Audience: External** и свой адрес ещё раз в контактных данных.
4. Откройте вкладку **Audience** и нажмите **Publish app**, чтобы статус стал _In production_.
   Прежде чем пропустить этот шаг, прочитайте блок ниже — для инструмента бэкапа он обязателен.
5. Откройте вкладку **Clients** → **Create client** → тип приложения
   **TVs and Limited Input devices** → задайте имя → **Create**.
6. Скопируйте **Client ID** и **Client secret**.
7. В Obsidian: _Settings → Geode_ → вставьте оба значения и нажмите **Connect**.
8. Появится окно с коротким кодом и ссылкой. Откройте ссылку на любом устройстве, где удобно
   печатать, введите код и подтвердите доступ. Окно закроется само.

> [!IMPORTANT]
> **Не оставляйте приложение в статусе _Testing_.** Любому External-приложению со статусом _Testing_
> Google выдаёт refresh-токен, который умирает через **7 дней**. После этого Geode будет раз в
> неделю падать с «Google revoked this connection» — и так всегда. **Publish app** решает это
> навсегда.
>
> Публикация здесь ничего не стоит. Вы остаётесь единственным пользователем, а `drive.file` — это
> **non-sensitive** scope: ни подачи на ревью, ни аудита безопасности он не требует. Если экран
> согласия предупредит, что приложение не верифицировано, — для приложения, которым пользуетесь
> только вы, это нормально: откройте **Advanced** и продолжите.
>
> Если вы намеренно оставляете статус _Testing_, сначала добавьте свой аккаунт в
> **Audience → Test users**. Этот раздел существует только пока статус _Testing_ — именно поэтому
> после публикации вы его не найдёте.

Geode запрашивает ровно одну область доступа: `https://www.googleapis.com/auth/drive.file`. Она даёт
доступ только к файлам, которые создал сам плагин, — прочитать что-либо ещё на вашем Drive он не
может. Широкая область `drive` не запрашивается никогда: это restricted scope, требующий платного
аудита безопасности, и инструменту резервного копирования там делать нечего.

Опубликованный токен всё же перестанет работать, если вы отзовёте доступ на
[myaccount.google.com/permissions](https://myaccount.google.com/permissions) или если полгода не
будет ни одной отправки и ни одной загрузки.

> **Вход не работает и Google отвергает device flow?**
> Значит, у клиента неподходящий тип. Либо пересоздайте его как _TVs and Limited Input devices_,
> либо переключите **Sign-in method** на _Redirect with PKCE_ в настройках. Этот способ открывает
> обычную страницу согласия Google, перенаправляет на адрес `127.0.0.1`, который не загрузится, и
> просит вставить содержимое адресной строки обратно в Obsidian. Некрасиво, зато не нужен локальный
> веб-сервер, а значит работает и на телефоне.

На диск записывается только refresh-токен. Access-токены живут в памяти и получаются заново по мере
надобности.

## Использование

Пять команд, все — из палитры команд (`Ctrl/Cmd+P`):

| Команда                    | Что делает                                                            |
| -------------------------- | --------------------------------------------------------------------- |
| **Push changes to Drive**  | Загружает новые и изменённые файлы. Остальное пропускает.             |
| **Pull vault from Drive**  | Скачивает весь бэкап. Никогда не перезаписывает и не удаляет.         |
| **Unlock encryption**      | Проверяет парольную фразу и кэширует ключ на сессию.                  |
| **Connect Google account** | Запускает вход в аккаунт.                                             |
| **Show backup status**     | Подключение, папка, число отслеживаемых файлов, состояние шифрования. |

### Типичный первый запуск

```
Connect Google account   →   Push changes to Drive
```

Первая отправка создаёт папку на Drive (имя по умолчанию: `Geode`) и загружает всё. Последующие
отправляют только изменившееся.

### Восстановление на новом устройстве

```
Установить Geode  →  вставить тот же client ID и secret  →  Connect  →  Pull vault from Drive
```

Pull скачивает все файлы и восстанавливает дерево папок из закодированных имён. Если в хранилище уже
есть файл по входящему пути, а Geode не может доказать, что они идентичны, входящая копия
записывается как `note (from drive).md` — при повторных совпадениях получаются `(from drive 2)`,
`(from drive 3)` и так далее. **Pull никогда не удаляет и не перезаписывает.**

### Как читать итоговую сводку

Каждый запуск заканчивается уведомлением:

```
Push finished: 12 uploaded, 3 updated, 486 unchanged.

2 skipped — changed on another device:
  Journal/2026-07-30.md
  Projects/roadmap.md
```

**Конфликт** означает, что копия на Drive изменилась с тех пор, как это устройство её записывало.
Geode не станет угадывать, чья сторона права: файл пропускается, а вам об этом сообщают. Разрешить
можно через pull — вы получите обе копии рядом — или вручную.

## Шифрование

По умолчанию выключено. Когда включено, файлы, чей путь совпал с одним из ваших префиксов,
шифруются **до** того, как покинут устройство.

- **Шифр:** AES-256-GCM, свежий случайный 12-байтовый nonce для каждого файла при каждой отправке.
- **Ключ:** PBKDF2-SHA256, 600 000 итераций, ключ 32 байта, случайная 16-байтовая соль на хранилище.
- **Контейнер:** `MAGIC "OBEV" | VERSION 0x01 | SALT (16) | NONCE (12) | ciphertext+tag`.

Ключ вычисляется один раз при разблокировке и кэшируется в памяти — вычислять его на каждый файл
означало бы подвесить Obsidian на любом реальном хранилище. Кэш очищается при выгрузке плагина. Сама
парольная фраза никуда не записывается.

### Что именно шифровать

По одному префиксу пути на строку в настройках. Правило намеренно тупое, потому что «умное» правило
означает файл, который вы считали зашифрованным, ушедший в открытом виде:

| Префикс    | Совпадает с                                 | Не совпадает с  |
| ---------- | ------------------------------------------- | --------------- |
| `Journal`  | `Journal`, `Journal/2026.md`, `Journal/a/b` | `Journalism.md` |
| `Journal/` | то же самое                                 | `Journalism.md` |
| `Journal*` | `Journal/2026.md`, `Journalism.md`          | `Diary.md`      |

Сравнение чувствительно к регистру, `*` имеет особый смысл только в конце, строки, начинающиеся с
`#`, игнорируются.

### Файл проверки парольной фразы

Первая зашифрованная отправка записывает в папку на Drive небольшой файл `__keycheck`. В нём лежат
соль хранилища и известная строка-маркер. Новое устройство скачивает его первым и проверяет вашу
парольную фразу **до того, как тронет реальные данные**: при неверной фразе всё прерывается
немедленно, ничего не изменив на диске.

### Ограничения, о которых нужно знать

- **Имена файлов не шифруются.** Пути кодируются в base64url, чтобы их принимал Drive, — это
  кодирование, а не шифрование. Любой, у кого есть доступ к папке, увидит все пути вашего хранилища.
- **Размеры файлов не скрываются.** Контейнер — это длина открытого текста плюс 49 байт.
- **Восстановления нет.** Забудете парольную фразу — зашифрованные файлы потеряны и для вас, и для
  всех остальных.
- Зашифрован файл или нет, решается по заголовку `OBEV` при скачивании, а не по расширению и не по
  флагу `enc` в метаданных Drive. И то и другое со временем расходится с реальностью, заголовок —
  нет.

## Аварийное восстановление без Obsidian

`tools/decrypt.mjs` работает автономно. Он ничего не импортирует из `src/`, ему не нужны ни
`npm install`, ни сборка. Скопируйте этот один файл рядом со скачанной папкой Drive — и вы вернёте
свои заметки, имея только Node и парольную фразу.

```bash
# Один файл в stdout
node tools/decrypt.mjs 5rWL6K-VLm1k

# Один файл на диск
node tools/decrypt.mjs 5rWL6K-VLm1k -o note.md

# Восстановить хранилище целиком из скачанной папки Drive:
# декодирует имена, расшифровывает зашифрованное, остальное копирует как есть
GEODE_PASSPHRASE='…' node tools/decrypt.mjs --dir ./downloaded-Geode --out ./restored

# Доказать, что этот инструмент согласуется с плагином
node tools/decrypt.mjs --verify-vectors test/vectors.json
```

Парольная фраза берётся из `--passphrase`, иначе из `GEODE_PASSPHRASE`, иначе запрашивается
интерактивно.

### Эталонные векторы

В `test/vectors.json` лежат четыре замороженных случая — пустой файл, короткий ASCII, UTF-8 с
кириллицей и эмодзи, и 1 МиБ бинарных данных. В каждом записаны парольная фраза, соль, nonce,
открытый текст и точный ожидаемый контейнер.

Две независимые реализации обязаны сойтись на всех: `src/core/container.ts` (проверяется
`npm test`) и `tools/decrypt.mjs` (проверяется `npm run verify:vectors`). CI запускает обе. Векторы
только добавляются: смена формата означает поднятие `VERSION` и добавление новых случаев, а не
правку существующих.

## Как определяются изменения

Geode считает файл устаревшим, сравнивая SHA-256 его **открытого текста** с локальным индексом в
`data.json`.

Это важнее, чем кажется. Зашифрованные файлы получают свежий nonce при каждой отправке, поэтому их
шифротекст — а значит и `md5Checksum` на Drive — меняется каждый раз, даже если сама заметка не
изменилась. Любая проверка устаревания по удалённым контрольным суммам заново загружала бы всё
хранилище при каждом запуске. Хеш открытого текста — единственный сигнал, который остаётся
неподвижным.

Удалённый md5 используется ровно для одного: заметить, что **другое устройство** переписало файл с
момента последней отправки. Это конфликт, и Geode отказывается его перезаписывать.

Хеш открытого текста никогда не покидает ваше устройство. Отправка его для зашифрованного файла
позволила бы кому угодно подтвердить догадку о содержимом.

Последствия, которые стоит знать:

- Push читает каждый файл хранилища, чтобы его захешировать. Это корректно, но не бесплатно на
  хранилище с большими вложениями.
- Потеря `data.json` не фатальна. Следующая отправка увидит файлы, о которых ничего не знает, найдёт
  их уже на Drive и сообщит о конфликтах, вместо того чтобы затереть. Pull перестроит индекс.
- `.obsidian/` никогда не попадает в бэкап. Именно там лежит `data.json`, а вместе с ним ваш
  refresh-токен Google.

### Как всё хранится на Drive

Плоско. Одна папка, один файл Drive на каждый файл хранилища, без повторения иерархии:

```
Geode/
  bm90ZS5tZA                    ← base64url("note.md")
  Sm91cm5hbC8yMDI2LTA4LTAxLm1k  ← base64url("Journal/2026-08-01.md")
  __keycheck
```

Путь живёт в имени файла, потому что `appProperties` в Drive ограничены примерно 124 байтами на пару
ключ/значение, а любой неASCII-путь это переполняет. В `appProperties` хранится только `{ v, enc }`.

Каждая загрузка явно указывает эту папку как родителя, поэтому ничего из записанного Geode не может
оказаться где-то ещё, — а `drive.file` не даёт плагину даже видеть остальной ваш Drive.

Папка создаётся в корне «Мой диск», и выбрать другое место плагин не предлагает: с `drive.file` он
не видит вашего дерева папок, и ему неоткуда взять id родителя. Хотите аккуратнее — **перетащите её
один раз мышкой в веб-интерфейсе Drive**. Geode обращается к папке по file id, так что переезд для
него незаметен; а если `data.json` когда-нибудь потеряется, запасной поиск идёт по имени без
ограничения по родителю и найдёт её там, куда вы её положили.

## Справочник настроек

| Настройка                     | По умолчанию | Примечания                                                     |
| ----------------------------- | ------------ | -------------------------------------------------------------- |
| Client ID / secret            | пусто        | Ваш собственный OAuth-клиент Google                            |
| Sign-in method                | Device       | Переключайте на PKCE, только если Google отвергает device flow |
| Drive folder name             | `Geode`      | Смена после отправки указывает на другую папку                 |
| Encrypt selected paths        | выкл.        | Включает список префиксов ниже                                 |
| Encrypted paths               | пусто        | По одному префиксу на строку                                   |
| Ask for the passphrase        | Раз в сессию | Или при каждой отправке и загрузке                             |
| **Mirror deletions to Drive** | **выкл.**    | Включено — локальное удаление навсегда убирает копию с Drive   |

> **О переносе удалений:** когда выключено, удалённый локально файл остаётся в бэкапе — обычно ради
> этого бэкап и заводят. Когда включено, отправка удаляет копию с Drive безвозвратно, минуя корзину
> Drive. Бэкап, который забывает то, что вы удалили, не сможет вам это вернуть.

## Разработка

```bash
npm run dev             # esbuild в режиме наблюдения
npm run typecheck       # tsc по src, test и tools
npm run lint            # eslint с проверкой типов
npm run test            # vitest по src/core
npm run verify:vectors  # автономный дешифратор против эталонных векторов
npm run format
npm run build           # всё сразу, затем production-сборка
```

### Структура

```
src/
  main.ts        жизненный цикл, команды, связывание — без бизнес-логики
  types.ts       брендированные типы, Result, AppError
  settings.ts    форма настроек, значения по умолчанию, миграция
  core/          чистая логика: container, kdf, path-codec, selector, diff, bytes
  drive/         auth-provider, device-flow, pkce-flow, client, dto
  ops/           push, pull, index-store
  ui/            settings-tab, модальные окна, progress
test/            vitest только по src/core — без моков и без заглушки Obsidian
tools/           автономный дешифратор, генератор векторов, бамп версии
```

Два правила сборка обеспечивает механически, а не по договорённости:

- **Ничто в `src/core/` не может импортировать `obsidian`.** Весь ввод-вывод внедряется извне —
  именно это позволяет тестировать криптографию и логику диффа в чистом Node без моков.
- **Ничто в `src/` не может трогать Node API.** В `tsconfig.json` задано `types: []`, поэтому
  `Buffer`, `process` и `require` не компилируются, а ESLint запрещает их вместе с `fetch` по имени.
  Весь HTTP идёт через `requestUrl` из Obsidian — единственное, что проходит мимо CORS в рендерере.

Проверьте сами: добавьте `Buffer.from('x')` в любой файл внутри `src/`, и `npm run typecheck`, и
`npm run lint` это отвергнут.

## Выпуск релиза

Две команды:

```bash
npm version patch     # или minor / major
git push --follow-tags
```

`npm version` поднимает версию в `package.json`, затем lifecycle-скрипт `version` синхронизирует
`manifest.json` и дописывает новую запись в `versions.json` — все три файла попадают в один коммит.
Пуш тега запускает [`release.yml`](../.github/workflows/release.yml): он заново прогоняет typecheck,
lint, тесты и эталонные векторы, собирает `main.js` и публикует GitHub Release со сгенерированным
описанием.

Три детали, в которых легко ошибиться и потом долго искать причину:

- **У тега не должно быть префикса `v`.** Obsidian ищет релиз по тегу, в точности равному версии из
  `manifest.json`, то есть `1.2.3`, а не `v1.2.3`. В [`.npmrc`](../.npmrc) задано
  `tag-version-prefix=""`, поэтому `npm version` создаёт правильный тег по умолчанию.
- **Файлы прикладываются по отдельности, а не архивом.** Установщик Obsidian забирает `main.js` и
  `manifest.json` прямо из релиза; `.zip` для него не существует.
- **`versions.json` живёт в основной ветке, а не в релизе.** Он сопоставляет версию плагина с
  минимальной версией Obsidian — именно так старым клиентам предлагают последнюю сборку, которую они
  ещё могут запустить.

Workflow откажется публиковать релиз, если тег расходится с `manifest.json`, `package.json` или
`versions.json`, а также если в собранном бандле обнаружится Node API. Релиз, сломанный таким
образом, на GitHub выглядит нормальным и просто никогда не доходит до пользователей.

Чтобы поднять минимальную версию Obsidian, отредактируйте `minAppVersion` в `manifest.json`
**до** запуска `npm version` — скрипт копирует в `versions.json` то, что там лежит.
